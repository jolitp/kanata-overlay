# Implementation Plan: Key Action Labels

**Branch**: `002-key-action-labels` | **Date**: 2026-10-23 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/002-key-action-labels/spec.md`

## Summary

Each physical key will show its action on the active Kanata layer.

- **Parser**: a new Qt-free crate, `crates/kbd`, parses the commonly used subset of the
  `.kbd` language: `defsrc`, `deflayer`, `deflayermap` and `defalias`. It turns each
  action into a short label: key glyphs, modifier symbols, layer arrows, and the tap
  action plus a hold marker.
- **Config path**: the app reads the file given with `--config` at start-up and again
  when Kanata reports a config reload.
- **Layer changes**: labels are recomputed in Rust on every layer change and pushed to
  QML as JSON.
- **Rendering**: `KeyCap.qml` renders the labels with fit-to-key text and styles for
  inherited, disabled and hold keys.

## Technical Context

**Language/Version**: Rust stable (edition 2024, MSRV 1.88); QML (Qt 6.11)

**Primary Dependencies**: none new. The `kbd` crate uses std only. One small Python script regenerates the key-name table from Kanata's source.

**Storage**: none; the config is only read (FR-004)

**Testing**: `cargo test -p kbd` (lexer, forms, aliases, transparency, every label rule, two fixture configs); the manual steps in [quickstart.md](quickstart.md) for rendering and reloads

**Target Platform**: Linux (unchanged)

**Project Type**: Desktop app (Cargo workspace)

**Performance Goals**: labels update under 100 ms after a layer change (SC-002); a reload is reflected within 2 s (SC-003)

**Constraints**:
- The parser is best-effort and lenient (FR-003, SC-005).
- No config text in logs (FR-013).
- `just check` stays green.

**Scale/Scope**:
- 1 new crate: lexer, reader, labels, and a generated name table of about 400 entries.
- Changes to `main.rs`, `overlay_state.rs` and `KeyCap.qml`.
- 1 new example config, the justfile and the README.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Status | How |
|-----------|--------|-----|
| I. Rust owns state, QML renders | ✅ | Parsing, alias resolution, transparency and label text all live in `crates/kbd`. `OverlayState` holds the parsed config and publishes `labelsJson`. QML only looks keys up. The config is read on the connection thread or a start-up thread, and results reach the QObject only through `qt_thread().queue(...)`. |
| II. Stable Kanata interfaces | ✅ | Layer and reload events still come from `kanata_client::protocol`. Parsing the user's `.kbd` file isn't a wire format. It is isolated in its own crate, lenient, and covered by fixture configs. Neither `RequestCurrentLayerInfo` nor debug output is used. |
| III. Never strand the keyboard | ✅ n/a | No processes are started and nothing is grabbed. |
| IV. Plasma Wayland first | ✅ n/a | Rendering only; it works on both overlay variants. |
| V. Testable without hardware | ✅ | `kbd` is pure and fully unit-tested with fixture configs. Kanata's own `--check` validates the fixtures. The one step that needs real Kanata (reload) has a manual note (quickstart §4). |
| VI. Key events are private | ✅ | No key events are involved. The config text is kept out of logs and notices (FR-013). |
| VII. Simple first | ✅ | A hand-written parser for the subset, as the constitution prescribes. No new crates. `defvar`, `include` and templates are left out and reported. |

**Gate result**: PASS. Nothing needs justifying.

**Note on II**: II's "behind a trait, per-version fixtures" clause is about *runtime channels to a running Kanata* that are less stable than TCP, such as debug-output parsing. The `.kbd` file is the user's own input, and VII names a hand-written parser for it explicitly. The spirit of II still holds:
- it is optional (`--config`);
- it is isolated in its own crate behind two functions (`kbd::read`, `kbd::labels`);
- it degrades gracefully (FR-003);
- it is covered by fixture configs, and the key-name table is regenerated per Kanata version (research R5).

**Post-design re-check**: still PASS. The generated key-name table is data, not a
dependency, and is regenerated by a script when Kanata is bumped. The R6 transparency
approximation is documented in research.md and in the label style ("inherited").

**Structure Decision**: Follow the workspace pattern: logic goes in a new library crate,
`kbd`, and the app only bridges it. The label rules live in `kbd`, not in `layout`,
because they depend on Kanata's action syntax, not on physical geometry.

## Implementation Notes

- **Order**:
  1. US1: lexer, `defsrc`/`deflayer`/`defalias`, simple keys, transparent and no-op, `--config`, `labelsJson`, `KeyCap`.
  2. US2: the rest of the action classifier and label rules, `deflayermap`, the all-actions fixture.
  3. US3: reload handling and notices.
- **Mapping**: physical key → canonical name is computed when the layout loads and added to the layout JSON as `kanataCanonical`.
- **Reload**: on `ConfigFileReload`, the connection thread reads and parses the file itself (cheap), then queues the result. On failure it queues only a notice.
- **No connection**: label the first layer (FR-010). `current_layer` stays empty until Kanata reports one.
